# 0004. 生成コードはマーカー区間の更新方式とする

- 状態: 承認
- 日付: 2026-09-24

## 背景

DSL から生成したコードと、ユーザーが書くコード（イベントハンドラの処理、独自の初期化など）をどう共存させるかを決める必要がある。
DSL を編集するたびに再生成するので、ユーザーのコードを壊さないことが必須。

## 検討した選択肢

- **ベースクラス継承方式**（Qt の `ui_*.h` と同様）: 生成ファイルは毎回丸ごと上書きし、ユーザーは生成クラスを継承して処理を書く。
  - 利点: 実装が容易。ユーザーのコードを壊す心配がない。
  - 欠点: クラスが2つに分かれ、ウィジェットやハンドラの定義場所が分散する。ユーザーは継承・仮想関数の仕組みを意識する必要があり、
    「Tkinter のように1クラスで素直に書ける」体験を損なう。
- **マーカー区間の更新方式**: ユーザーのクラスの中にマーカーで囲んだ生成専用区間を置き、再生成時はその区間だけを書き換える。
  - 利点: 1クラスに完結し、手書きした場合と同じ形のコードになる。
  - 欠点: 既存ファイルを安全に部分更新する仕組みが必要で、実装難易度は大きく上がる。

## 決定

**マーカー区間の更新方式を採用する。** 実装コストよりユーザー体験を優先する。

マーカー区間は次の2種類とする（詳細は [codegen-design.md](../codegen-design.md)）。

1. **宣言部**: DSL 上のすべての Tk オブジェクト（ウィジェット・変数）の宣言。C++ ではヘッダのメンバ宣言、Python ではコンストラクタ内の属性。
2. **予約メソッド**: 次の3つのメソッドの宣言と実装。
   - A. ウィジェット・変数の生成、親子関係の紐づけ、オプションの設定
   - B. レイアウト情報に従った配置
   - C. イベントバインディング

予約メソッドの呼び出しは、初回生成時にコンストラクタに用意する。

## 影響

- 初回生成（ファイル一式の雛形作成）と、2回目以降の更新（マーカー区間の置換）は別の処理として実装する。
- マーカーの欠落・重複、区間内の手編集、フォーマッタによる書き換えなど、部分更新特有の異常系への対策が必要（codegen-design.md の論点）。
- 部分更新ロジックは VS Code に依存しないコアパッケージに置き、拡張と CLI の両方から使う。
- 部分更新ロジックはテストで厳密に守る（ゴールデンファイルによる入出力テストを想定）。
